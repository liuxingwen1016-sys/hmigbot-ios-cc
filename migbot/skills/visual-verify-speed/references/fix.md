# 修复子代理任务书

主会话按 `spec/visual-verify/rounds/round-N/fix/schedule.json`（摘要见 `docs/autofix-log/round-N/batch.md`）派你修**一个组**：组里的问题单路径（`tickets`，在 `spec/fix/round-N/` 下）和你可以改的文件（`write_set`）。同一波里别的组由别的子代理同时在修，所以：

1. **只改 `write_set` 里的文件**（可以新建本组需要的新文件，例如新组件、新资源）。发现必须改别的文件（共享 ViewModel、入口页、路由表；多个页面共用的宿主页默认不在写集里）时，不要改，写进结果文件的 `needs_file`，主会话等这一波结束后处理。`unlocated` 组单独运行，可以改任何文件。改了写集以外的文件会被 `fixcheck` 抓出来、整组退回。
2. **改完一个文件就落盘**，不要攒到最后一起写。
3. 不编译、不装机、不截图、不跑 vvs.py；主会话在所有修复结束后统一编译一次，下一轮走查复验。
4. 无依赖的读取一次发出（问题单、对比图、dump、安卓源码、鸿蒙源码一起读）。
5. **不写 disposition**，只改代码并追加 §6 修复记录；修没修好只由下一轮复验判定。

## 每张问题单怎么修

1. **三层证据，不跳层**：
   - 视觉：先 Read `evidence` 第一张对比图（`screenshots/sbs/…`，左安卓、右鸿蒙），列出看得见的差异；
   - 结构：再读 §1.5 的两端 dump（`.android.xml` / `.hmos.json`），确认差异在结构上是什么——真没渲染、被遮挡、滚出屏幕、条件渲染没进分支、层级不对。只看图会把"被挡住"当成"没有"去加重复元素；
   - 源码：最后读 §1 / §1.5 的安卓源码和 `suggested_files` 里的鸿蒙实现，锁定负责这块 UI 的页面、组件、状态来源。
2. **同一页一次修完**：组里同一页的几张单先全读完，列出这一页全部差异和要改的位置，一次改好，不来回改同一个文件。
3. **取值只认安卓源码**：在布局 XML、style、dimen、color、drawable、代码里找到真实取值，记下 `file:line`。dp→vp、sp→fp、颜色 hex、圆角按 1:1 用；语义不 1:1 的别照抄字面值——状态栏/安全区避让（鸿蒙沉浸式和标题栏组件常已自带顶部避让，外层别再加；底部手势条区不能让底栏、按钮压上去，不要为了贴近安卓的底边删掉底部避让；顶部同理，状态栏避让保留，安卓沉浸式页面里用来垫状态栏的那段留白在鸿蒙上不要再加一遍）、字重映射、Toast 时长（短≈2000ms、长≈3500ms）。从截图估的数（"约 234px""偏深"）不能当取值依据；找不到出处就在结果里写 `blocked` 和原因。
4. **行为类缺陷**（点了没反应、关不掉、跳错页、状态不变）：
   - 先读到安卓里**承载这个行为的组件源**：弹框按钮的 `setOnClickListener`、列表的 adapter / ViewHolder、自定义控件类——页面级源码通常不够；
   - "点了没反应、但系统返回键有效"先查**命中链**：从按钮往上的祖先容器有没有 `hitTestBehavior(visible ? HitTestMode.Block : …)`。只有 `Block` 会挡住全部子节点，"显示时 Block"永远是缺陷（隐藏时 Block、纯遮罩、叶子自身才合法）；
   - 再查**装配入口有没有接线**：按钮最终调用的服务 / 客户端 / 单例是否真被实例化和注册（守卫函数报"未配置/未就绪"时，数一数装配入口在定义处之外的调用点，0 个就是没接线）。
   - `CRASH_*_nav_failed_*` 按 `v4_edge.nav_mismatch_type` 修：`missing_handler` 补入口和点击跳转（目标页面不存在就按安卓实现一个）；`wrong_target` 改路由目标或跳转参数；`semantic_diff` 让该位置的控件与安卓一致。`suggested_files` 是显示入口文字的鸿蒙文件（入口控件所在处）；`blocks_subtree` 里的页面修好后下一轮一并重采。
5. **完整实装**：加按钮要同时有 `onClick` 和真实行为，不留 `/* TODO */`；加弹框要有触发、控制器和内容；用 `$r('app.media.xxx')` 前确认资源文件存在，用 `$r('app.color.xxx')` 前确认 token 在 `color.json` 里，不在就先建；资源缺失时从安卓工程转过来，不要手画图标；文案走 `$r('app.string.xxx')`。遵守工程现有写法（状态管理 V1/V2、命名）。
6. **最小侵入**：只改有问题那一块，不顺手重构、改名、改方法签名、调 import 顺序。
7. **顺手看到的差异**：同一页上看到单子之外的差异，一并修好，并在 §6 摘要里写明；别的页不碰，写进结果文件的 `side_findings`。
8. `ui/_systemic/SYSTEMIC_*` 单：在共用组件或样式里改一处，再逐张核对 `affects` 里的成员单。`BLOCKED_*` 是占位单，不修；`disposition` 为 `manual_review` / `skipped` / `wont_fix` 的不修。

## §6 修复记录

在问题单 `## 6. 尝试过的修复方案` 下追加一段（不删历史；子段标题一字不改，下游按这一行计数）：

```markdown
### round-N attempt by visual-fixer
- **改动文件**：`entry/src/main/ets/pages/XxxPage.ets:120-135`
- **改动摘要**：标题文字色由 #999999 改为安卓 colors.xml:12 的 #333333
- **假设根因**：迁移时颜色取了默认次要色
- **预期效果**：下一轮标题颜色与安卓一致
- **未做的事 / 已排除的可能**：未改字号（对比图里字号一致）
```

- "改动文件"写真实路径（带行号），不许写"无 / - / N/A"；声明的文件没有变化会被 `fixcheck` 判为空改。
- "改动摘要"引用用到的安卓取值和出处（文件:行）；改动类型要和问题对得上（字体问题改字号/字重，颜色问题改颜色……），对不上会被判为改错地方。
- 单里写着"顽固问题"或"上轮修复复核：…"时：先读完 §6 全部历史；不许重复任何一条历史的"假设根因 + 改动摘要"，也不许只把同一个值再微调一点（#2a→#2c→#2e）；换文件、换属性、换层级或换根因假设，并在"未做的事 / 已排除的可能"里写明排除了哪些方向。

## 结果文件

写到 `spec/visual-verify/rounds/round-N/fix/<组名>.json`：

```json
{"group": "g01",
 "changed_files": ["entry/src/main/ets/pages/SettingsPage.ets"],
 "tickets": [{"id": "ALIGN_P0072_color_mismatch_title-color", "status": "fixed", "source": "item_setting.xml:42", "note": ""}],
 "needs_file": [{"file": "entry/src/main/ets/viewmodel/SettingsVM.ets", "why": "标题颜色映射在共享 VM 里"}],
 "side_findings": [{"page": "P0073", "what": "列表分隔线比安卓粗"}]}
```

`status`：`fixed`（已按出处改完）| `blocked`（找不到出处或需要产品决策，写原因）| `needs_file`（要改写集外的文件）| `refuted`（核对后认为问题单不成立，`note` 写证据：两端 dump 里都有该节点、安卓源码本来就是这样等；不改代码）。`blocked` / `needs_file` / `refuted` 的单不要求 §6 记录，`fixcheck` 按结果文件记为"修复方未改"并把原因带进下一轮；`fixed` 的单必须有本轮 §6 记录。是否真的修好、是不是误报由下一轮复验判定，不由你自报。
