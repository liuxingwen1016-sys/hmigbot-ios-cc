# 先决条件与共享依赖审计

使用当前 contract 的实际调用链建立后置条件。以下检查适用于需要异步资源、外部请求或持久化的动作；普通局部点击将不适用的角色标为 `NOT_APPLICABLE`。不要把媒体、文件或特定布局强加给所有动作。

## 从可见动作确认实际派发

对状态驱动按钮，逐项对齐当前 label/icon、实体状态、组件内分支与最终命令。
父组件传入 `onPlay` 只证明提供了回调，不能证明当前点击会走该回调；继续展开
子组件的下载中/未下载/已下载分支及其它事件消费者。以 Android 对应状态下的
动作工厂或 dispatcher 为 oracle，区分串流、下载、本地播放、取消与暂停。
串流/下载偏好也属于当前条件，保留 Android 的选择策略，不把所有未下载项
一律改成播放或下载。
播放图标进入下载分支、禁用门恒为 false 或两种动作共享错误占位回调，都是要
审查的具体断点；不能只改图标来掩盖应有的业务命令。

把“入口 × 用户报告的数据状态 × 实际分支 → Android 终态”写入既有
`effect_chain` 和角色证据，不新增独立流程。不同入口或状态的回调可以共享
service，但另一条分支成功不能代替当前分支；统一错误提示也不能证明两条
路径执行了相同领域命令。

## 前置资源的生产者必须可先执行

对每个 `await`、状态 guard 或 callback 等待，指出：它等待什么、由哪个方法/生命周期产生、该生产者何时可达。沿依赖检查是否存在“等待完成 → 才挂载页面/资源 → 该资源才允许完成”的循环。典型资源包括 surface、组件实例、权限结果、连接、会话和订阅。

对条件挂载与显隐状态，按“初值 → 父组件挂载条件 → 子组件订阅/生命周期是否安装 → 状态写入者”检查启动路径。若使条件成立的唯一写入者要等该条件成立后才挂载，源码已足以确认循环；不能仅因涉及运行时顺序就归为 `CONFLICTING_EVIDENCE`。确有外部写入者或另一条激活路径时，引用其实际可达证据再裁决，不假设页面会自行显示。

若源码已证明循环或生产者永远不可达，这是 `STATIC_REQUIRED`，即使设备不可用也应修复。工单同时包含等待方和资源生产方。复用既有的页面激活、资源就绪回调或命令调度，将开始请求与完成通知分开；保留失败、取消及重复请求的身份约束。增加超时、吞错、提前返回成功不解除依赖。

对异步任务分别核对命令受理、执行中和终态后的行为。若 Android 允许执行中观察或取消，受理后即须通过真实任务身份投影相应状态与操作入口，终态后回读真实结果；不能把这些运行中交互延后到任务结束。`ASYNC_TERMINAL` 要求有可信的终态确认来源，不要求点击 Promise 等待整个任务。Android 不提供的进度、取消或运行中操作不额外补造。

把具体事实写入既有 `ENTRY_SIDE_EFFECTS`、`DOMAIN_COMMAND`、`ASYNC_TERMINAL` 的 expectation/evidence；运行中交互与终态回读分别落入 `OBSERVABLE_STABILITY`、`READBACK`，无需新增字段、流程或固定节点数量。

对异步消费者，继续定位当前视图实际渲染的属性：它是直接响应式绑定，还是 `map/spread/copy` 得到的本地快照。沿终态通知追到同一份状态的写入与刷新；仅调用命令受理后的 reload 或修改 service 单例，不能证明另一份页面快照更新。把可证明的终态投影断链落入现有 `INVALIDATION/READBACK` 义务与具体 owner targets；已有响应式更新证据时不强制新增 observer，不增加候选或另开审查。

## 核对有效输入到最终命令的参数

从 Android 的当前 action 分支提取实际参数，再逐跳核对 ArkTS 到最终平台调用的传递。检查实体与资源身份、URL、认证来源、headers/cookie、执行模式和可取消的请求身份。字段在模型中存在、服务接收了 request 对象，都不能证明最终命令收到它；检查赋值、默认值、复制和重建对象的位置。

输入检查从用户实际失败的对象开始。按其入口追踪“获取/解析 → 合并与持久化 →
列表或路由重读 → 命令参数”，并与 Android 对应分支比较；不能从人为假设的
有效 URL 开始跳过前半段。数据缺失若由仓内生产者造成，属于静态修复范围；只有
源码链完整而外部资源确实不可用时，才记为外部证据缺口。不同入口共享同一
repository 时仍需核对各自读取的 ID、媒体记录和参数副本。

对媒体订阅的实际格式，核对 enclosure/link 的属性提取、XML 实体解码、相对地址
解析与媒体类型；只测试某一种 RSS 写法不能证明另一个实际使用的格式完整。
检查同一单集刷新合并是否保留媒体身份、本地路径和下载状态，避免重复插入后
重读到旧行。先用源码或目标对象的脱敏数据证明断点，再把必要 producer/store
加入该点击的 edit targets；不扩展为全库重构，也不凭格式风险直接开缺陷。

“出了点问题”等统一错误文案只证明失败被展示。沿 catch/终态结果找原始错误码、
发生阶段和 item/media/task 身份，区分输入校验、任务创建、传输、文件和提交失败。
允许读取已授权设备的相关日志或只读数据副本；缺少可归因错误时保留具体缺口，
不能凭相同 toast 推断播放与下载根因相同，或通过更换 toast 宣称修复。

常规诊断可在冻结修复 targets 前使用用户已提供或已授权获取的诊断证据。用户要求
“Skill 独立修复，跑完再验收、只报告不修复”时，修复阶段只用本次允许的源码/SDK
输入，不提前操作设备，也不将验收发现回灌修复。先封存 Skill 结果，再执行独立验收，
见 [真机验证契约](runtime-validation-protocol.md)。用户禁止设备操作时只读允许的
现有证据与源码。常规设备取证由主流程串行执行，记录安装版本、对象与时间；旧安装
的失败能帮助定位，不能证明本轮补丁已通过真机验证。
静态检查的条件性风险遇到实际同类错误时应重新核对可达分支：例如已有目录加
`File exists` 需查目录准备和最终文件提交两处，不能沿用“未实测所以不处理”。

凭据使用来源与是否传递的证据，不把真实密码、token 写进审计产物。对公开数据不强加认证；只在 oracle 及当前场景要求时检查对应链路。

额外预检、目录创建或重定向也是命令的前置。检查它们失败是否阻断 Android 仍能成功的主命令；例如服务只支持 GET 时，额外 HEAD 失败不能被当作 GET 必然失败。目录存在性需沿实际执行分支核对：另一个分支的检查、未调用的 helper 或附近出现错误码不构成保护；递归参数和 SDK throws 清单也不能单独证明安全或必错。

按当前 SDK 声明核对 callback 字段单位和形状。已确认使用 `request.agent.Progress`
时，区分已处理量 `processed`、各文件总大小 `sizes` 及当前索引 `index`；多文件与未知
大小还需核对 SDK 的具体约定，不能把 `sizes[0]/sizes[1]` 当成通用进度公式。
guard 只对可识别的 API 类型或 Task 回调提出候选，不凭文件名或无关数组运算判缺陷。

## 在冻结 ownership 前把第一处断链送进工单

Baseline packet 中的 scope hazard 是定位提示。Reviewer 打开 owner 源码，建立当前点击到该 owner 的调用/状态依赖，再与 Android 后置条件核对。确认缺陷后，`edit_targets` 同时包括真实断点 owner 和必要的入口/消费者；仅把页面列为目标会让后续 agent 无权修共享服务。

这里的调用依赖包含本次计划接通的预期路径：首个 handler 未实现时，仍需检查接通后必经的共享前置和消费者。仅确定首断点不足以排除后方已有候选。平台语义无法确认时按 scope 协议记录实际查询与缺失事实；Repair 获得新 SDK 依据后通过 static_handoffs 交接，不能让旧的“未进入平台”结论覆盖修后事实。

不要凭 `primary/secondary`、页面名或同属一个领域，将某个 service hazard 分给任意点击。无法建立归属的 hazard 保留为证据缺口；`UNREVIEWED` 不得被脚本升级为 `FIX_REQUIRED`，也不得由脚本生成 Android oracle 或替换人审根因。

Quick Review 必须先读取当前源码的 scope，再冻结 Round 2 targets。Round 1 的 `OWNERSHIP_INSUFFICIENT` 若有新增且证据明确的 owner，就在此处补入。超过既有路径预算时明确列出剩余 owner 与阻塞原因，保留 deferred；不要截断目标后宣称已闭合，也不在已冻结的 repair batch 中越权编辑。

路径相交只决定读取上下文。已绑定与未归属的 scope 候选（包括 `CONDITIONAL_RISK`）
都由 Reviewer 按 `hazard_id` 裁决实际依赖，再区分确认缺陷、已有保护和证据未决。
父组件已满足宿主条件、目录已有有效保护等，以具体源码证据排除并绑定源码 SHA；
来源不变时复用有效裁决，变化时重新核对。不能为了清零改造本已有效的结构。
未决候选阻止关闭，但不阻止其它已确认断点生成有界修复及如实记录 `PARTIAL`。

## 区分静态修复和实际可用

静态已证明的缺口与设备、网络、测试数据缺口分别回填既有九个角色。可编辑的前置资源顺序、参数丢失和错误状态投影不能归为纯 runtime gap。平台真实完成、实际音视频输出或最终文件内容仍需运行时证据。

全量执行的交付摘要列出领域入口是否进入 Review、剩余静态 blocker/owner、尚未执行的运行时场景。只有构建和安装时使用 `INSTALLED_UNVERIFIED`；两轮结束仍有问题时保留真实结果，不承诺已经可用。用户禁止 UI 操作时遵守限制；自动发现领域不产生额外设备操作授权。
