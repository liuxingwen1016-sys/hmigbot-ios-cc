# 深度理解原版设计

## 核心设计理念

### 1. 为什么这么复杂？

**不是过度设计，而是生产级系统的必要复杂度**

原版处理的是：
- 10万+行 Android 代码
- 100+ 页面
- 复杂的依赖关系
- 需要 20-30 个 Agent 并行工作
- 耗时 2-3 小时
- Token 消耗 500K-1M
- 成本 $10-20

这个规模下，必须有严格的：
- 并发控制（防止冲突）
- 质量门控（防止错误传播）
- 可追溯性（出错可定位）
- 可恢复性（断点续跑）

### 2. 关键机制解析

#### 2.1 findings 闭环

**问题**：如何确保问题真的被修复了？

**方案**：
```
linter 报告问题 → findings
    ↓
修复代码
    ↓
linter 重跑 → 不再报告 → 自动关闭 finding
```

**铁律**：
- findings 只能由 linter 重跑确认关闭
- 不能靠 Agent 声称"已修复"
- 防止假修复、假通过

#### 2.2 Stage/Slice/Batch 分层

**Stage** - 大阶段：
- Stage 0: UI 前置（资源转换）
- Stage 1: UI 转换
- Stage 2: Base 层
- Stage 3: Feature Slices

**Batch** - Stage 1 的并行单位：
- 每批 20-30 个页面
- 批内页面并行转换
- Batch 收尾 subagent 处理共享文件

**Slice** - Stage 3 的功能切片：
- 每个 Slice 对应一个功能模块
- 按依赖关系分组
- Group 内并行，Group 间串行

**为什么分这么细？**
1. 并行度：Batch/Group 可以并行执行
2. 隔离性：每个单元职责明确
3. 可恢复：单元失败可以重试
4. 可追踪：进度清晰

#### 2.3 共享文件单写者纪律

**问题**：20+ Agent 并行工作，如何防止冲突？

**方案**：
```
Worker Agent:
  - 只写自己的页面文件
  - 禁止碰共享文件
  - 例外：registry append（发号协议）

Closer Agent (收尾):
  - 唯一可以写共享文件
  - 处理跨文件接线
  - 回写状态账本
```

**为什么这样设计？**
- 避免并发冲突
- 责任清晰
- 可审计

#### 2.4 编译门的设计

**不是每个文件转换后都编译**

**编译时机**：
1. Base-7：Stage 1+2 完成后（第一道门）
2. Stage 3 集中门：每个 Group 完成后
3. FV-2：最终全量编译

**为什么不频繁编译？**
1. 编译慢（大项目需要 10-20 分钟）
2. 批内可能有依赖，编译会失败
3. 集中编译，批量修复更高效

#### 2.5 占位规范

**问题**：有些功能暂时实现不了，如何标记？

**错误做法**：
```typescript
// TODO: 实现这个功能  ❌ 自由文本
function foo() {}     ❌ 空实现
```

**正确做法**：
```typescript
// PLACEHOLDER: thirdparty-sdk-F023  ✅ 已登记
```

**必须在 registry 登记**：
- kind: 7类（thirdparty-sdk, complex-logic 等）
- trigger_condition: 什么时候实现
- fallback: 临时方案
- owner: 谁负责

**为什么这么严格？**
- 可追踪：知道有多少欠账
- 有计划：知道何时解决
- 可统计：覆盖率准确

### 3. iOS 版本需要保留的机制

#### 必须保留：
1. ✅ findings 闭环
2. ✅ Stage/Slice/Batch 分层
3. ✅ 共享文件单写者
4. ✅ 编译门设计
5. ✅ 占位规范
6. ✅ 可追溯性（digest）
7. ✅ 断点续跑

#### 可以简化：
1. ⚠️  iOS 项目通常更小（可以减少 Batch 大小）
2. ⚠️  SwiftUI 依赖更简单（Group 规模更小）
3. ⚠️  但核心机制必须保留

#### 我的错误：

**关键点**：
