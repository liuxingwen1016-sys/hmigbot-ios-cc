### 2.1 优化方法

本工具采用“源事实 → 交付契约 → 代码生成 → 确定性门禁 → 真机证据”的闭环。每次优化都要同时改变工具行为和验收证据，不能只修改提示词后宣称效果提升。

1. **先提取源事实**
   - i2h-spec 的 `ui_evidence.py`、全量源码索引和 iOS Simulator 采集共同生成页面、状态、交互、呈现关系和视觉触发器。
   - 原始 `cuike-ios` 只读。任何目标端修复都不能反向修改 iOS 源码来降低差异。

2. **再锁定交付契约**
   - i2h-plan 生成 `ui-delivery-approved.json`、页面责任、输出文件、sheet/full-screen 归属和状态覆盖。
   - execute 阶段只能按批准契约生成，不能通过修改 inventory 掩盖缺失页面或改变页面责任。

3. **把高风险经验变成确定性门禁**
   - 提示词负责告诉 Claude 应该怎么生成。
   - Python gate 负责判断生成结果是否满足结构不变量。
   - 真机/模拟器证据负责判断结构是否真的能点击、呈现和恢复。
   - 只有提示词没有 gate 的规则不算完成，只有静态 gate 没有运行时证据也不算功能完成。

4. **优先修复跨平台语义错误**
   - safe-area 不是简单加固定 padding，而是 WindowModel、根容器和页面前景三层协同。
   - sheet/full-screen 不是普通路由，必须保留 owner、dismiss、onDisappear 和下一层呈现顺序。
   - `@ObservedV2`、`@Trace`、`@Local` 等状态所有权必须保持 ArkUI 的可观察语义。
   - SwiftData/SQLite 到 relationalStore 的转换必须覆盖首装、二次冷启动和旧版本升级。

5. **每轮只解决可归因的问题**
   - P10 暴露了 safe-area、模态时序和视觉占位问题。
   - P11 真机又暴露了数据库 count、路由观察和 schema migration 问题。
   - 本轮门禁围绕这些真实反例增加，避免凭感觉堆叠规则。

1. 读取当前插件分支和实验状态。
2. 明确本轮唯一优化假设和验收指标。
3. 修改最小范围的 skill、prompt、gate 或测试。
4. 先跑插件本地测试。
5. 提交本地 commit，确认可回退。
6. 创建新的 `CuikeTemp` 派生工程运行 Claude。
7. 检查 transcript 中确实调用了 `Skill(hmigbot-ios:i2h-spec)` 等阶段。
8. 读取 marker、HAP SHA、阶段耗时、token、截图和 UI tree。
9. 用真实设备补做 CHECK-3/5，必要时补 CHECK-4。
10. 记录 PASS、WARN、BLOCKED 和根因，再决定下一轮。

### 2.3 实验编排方法

#### 独立工程

每个完整实验都从模板复制，不能在同一个工程上覆盖多轮结果。

```bash
ditto /Users/liuxingwen/DevEcoStudioProjects/CuikeTemp \
  /Users/liuxingwen/DevEcoStudioProjects/CuikeP13
```

实验工程只用于一次完整流水线或一次明确的 targeted follow-up。原始 iOS 工程和其他实验工程不参与写入。

#### 单一变量

- 同一轮使用同一个 iOS 源码快照。
- 同一轮使用同一个 Claude Code 版本和 `deepseek-flash[1m]`。
- 同一轮固定相同设备、分辨率、HAP 安装方式和截图算法。
- 只改变插件 commit 或明确记录的目标工程修复。
- P0/P1/P2 不混写结果。P0 负责功能阻断和数据一致性，P1 负责结构与视觉，P2 负责平台能力差异。

#### 减少重复运行

- 插件规则改动后，先用已有 P10/P11 工程做静态 gate 复扫，确认规则能抓住已知反例。
- 只有需要验证 Claude 是否会根据新规则生成不同代码时，才创建新的完整 Cuike 实验。
- 已有 spec/plan/execute 产物只做 targeted verify，不重复跑完整流水线。
- 只有源事实、交付契约或插件生成逻辑发生变化，才重新跑 spec/plan。
- 设备验收失败但源码未变时，只重跑 verify，不重跑 execute。

#### 实验记录

每个完整实验必须记录：

- 工程目录和来源模板
- 插件 commit
- Claude session ID
- 模型名称

- 功能路径状态和阻塞原因
- gate JSON、verify report、retrospect report

### 2.4 验收指标和判定方式

#### UI 完备度

UI 不能只看一个 pHash 数字，必须同时满足：

1. 页面和关键状态全部可达。
2. 页面标题、主操作、表单、sheet、full-screen、tab、图表、网格和资源图标存在。
3. safe-area、顶部操作和底部手势区不遮挡。
4. pHash、内容裁剪分数和人工结构对比均达到目标。
5. iOS/HarmonyOS 平台差异单独记账，不能把功能缺失归类为平台差异。

#### 功能完备度

至少覆盖：

- 首次启动和种子数据
- 二次冷启动
- 覆盖升级旧数据库
- Tab 切换
- 新增、编辑、搜索、详情、删除或归档
- Settings sheet
- Recipe sheet
- Brew full-screen
- pending/resume
- 深链冷启动与热启动
- OCR/相册/相机降级
- 通知和服务卡片

任何关键路径 BLOCKED 都不能宣称功能 100%。

#### 时间

正式流水线按 `i2h-spec → i2h-plan → i2h-execute → i2h-verify` 统计。targeted follow-up 不计入完整流水线耗时，但必须单独记录。P11 完整流水线约 51 分钟，满足时间目标，质量目标仍未达成。

### 2.6 API、设备和卡死处理

- Claude transcript 超过 300 秒没有新文件、命令或报告时，先检查实际子进程和产物。
- 有子进程继续运行时，继续等待并轮询同一个 job，不要重复创建实验。
- 子进程退出且状态为 failed/stopped 时，保留日志并判断是否可以从已有产物续跑。
